# Website quality contract

The owner requires Lighthouse scores at or near 100 for current and future work. The target is **100** in all four standard categories; deployment requires **Performance ≥97, Accessibility 100, Best Practices 100 and SEO 100** for the homepage. Mobile and desktop use three clean Lighthouse navigations each and the median category score. The public credits utility is intentionally `noindex`: it receives the same performance/accessibility/best-practices checks, with its SEO exclusion printed explicitly. Private account, admin, kitchen, history and review pages must retain `noindex`.

Run `npm ci`, `npm run audit:quality`, and `npm run test:browser -- tests/accessibility.spec.js`. The audit builds the repository subpath, serves only bundled sample menu/business data, and never authenticates to production, submits forms or reads private records. Reports are saved to ignored `quality-results/` and uploaded by Actions for seven days. The deployment job checks code, isolated tests, Lighthouse and representative accessibility/responsive journeys before building the production-configured artifact. Lighthouse runs alone in the workflow to avoid browser-test CPU contention. Chromium/Chrome must be installed; set `CHROME_PATH` locally if discovery cannot find it. `QUALITY_RUNS=1` is available for diagnosis; CI always runs three.

Axe browser checks cover public, sign-in, customer history, admin and kitchen screens in isolated authenticated fixtures at mobile and desktop widths, including contrast and label/visible-name consistency. Existing responsive tests cover 320–1440px. Keep manual keyboard, screen-reader, zoom and real-device checks: automated scores do not prove complete accessibility.

The local gate is a reproducible source/build regression check. A live Supabase backend, different phone CPU, network conditions, extensions, stored IndexedDB/service workers and Lighthouse versions can change measured production scores. For production spot checks, use a fresh browser profile or incognito, the correct Pages subpath, and the same Lighthouse version/settings; save the HTML report and compare several runs. Never clear a visitor’s guest session to improve a score. The experimental Agentic Browsing preview is not one of the four standard percentage categories. With the pinned Lighthouse version it is also checked at 100 (both scored checks passing), including accessible-tree validity and layout stability.

Responsive WebP derivatives are generated from the existing licensed JPEGs at build/start time. Original files, source hashes, credits and JPEG fallbacks remain. Cloud/custom menu photos retain their exact source; bundled local photos use smaller variants. Do not substitute a different photo to reduce bytes. Generated assets and audit results must not be committed.

Fix regressions before release. Do not lower budgets, hide real content, alter protected-page indexing, suppress audit rules or replace failing functional checks just to obtain a higher score. Update this contract only when the owner explicitly changes the requirement.

The site stylesheet is bundled in its original cascade order into generated `public/assets/site.css`; do not edit that generated file. Run a production-configured `npm run build:pages` again before manually publishing after an audit build.
